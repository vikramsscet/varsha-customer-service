# 01 — User & Authentication: Physical Database Design

**Status:** DRAFT. The five owner decisions in §10 were **accepted by the project owner on 2026-10-25**; the design as a whole is **not yet approved** because the infrastructure evidence in §10 has not been produced. This is a design document only. **No SQL has been executed, no migration file exists, no role was created, and no connection was tested.** Nothing here authorizes implementation.

**Authorization:** drafted on the project owner's instruction (2026-10-25) after the consistency re-check of Steps 5f and 5g.

**Sources:** [requirements.md](requirements.md) (§12.9, §12.10), [data-model.md](data-model.md) (§13 to §18 govern), [security-design.md](security-design.md) (§2.1, §8, §13, §18.5, §20), [api-contracts.md](api-contracts.md).

**Labels:** **[Decided]** = already approved in a source specification (cited). **[Proposed]** = a design choice made in this draft; needs your approval. **[Open]** = cannot be decided without evidence or an owner decision. **[Evidence]** = depends on a check in security-design §20 that has not been performed.

Placeholders `<owner_role>`, `<app_role>` and `<schema>` stand for names that are **not chosen**. No credential, connection string or role name is recorded. Column and table names below are **[Proposed]** and descriptive.

## 1. Scope and assumptions
- In scope: the five logical entities (Customer, Refresh Session, Refresh Token, Security Event, Sign-in Nonce), constraints, indexes, privileges, transaction boundaries, cleanup and migration approach.
- Out of scope: rate-limit state (in-process, single instance, security-design §11.1), access tokens (stateless), Cart, Checkout, Order, Payment, Delivery, Feedback, any Supabase Auth or Data API usage.
- **Connection method [Open, Evidence #1–3]:** this design uses only features that work on a direct connection **and** on the session-mode pooler (explicit transactions on one connection, savepoints, ordinary prepared statements). It uses **no** transaction-mode-pooler-incompatible feature (no session-level state, advisory locks or `LISTEN`). It therefore does not depend on the connectivity result.
- PostgreSQL version: **[Evidence]** not known. Features assumed: database-side random UUID generation, `timestamptz`, partial and expression indexes, savepoints, column-level privileges, row-level security. Availability is verified by check 15.

## 2. Schema placement and exposure
- **[Decided]** The authentication tables live in a schema that is **not exposed** through the host's HTTP APIs, nothing is granted on them to the roles those APIs use, and the owner and application roles are separate (`USER-SEC-016`, `USER-SD-AC-037`).
- **[Proposed]** One dedicated schema `<schema>`, owned by `<owner_role>`. No table is created in the default public schema.
- **[Evidence]** Whether the host exposes the schema by default, and which roles the HTTP APIs use, is verified by checks 6 to 8. Until then no exposure claim is made.

## 3. Common conventions
| Item | Design |
|---|---|
| Identifiers | **[Decided]** UUID v4 generated by PostgreSQL (data-model §15.6). Column default uses the database's random UUID function; the application does not generate identifiers. **[Evidence #15]** |
| Timestamps | **[Proposed]** `timestamptz`, stored and compared in UTC; set by the database clock (`now()`) unless a value is derived (expiries). |
| Digests | **[Proposed, needs approval]** SHA-256, stored as `bytea` (32 bytes). Applies to refresh-token digests, the CSRF-token digest, the nonce digest and the binder hash. Inputs are high-entropy random values (≥256 bits for tokens), so an unkeyed digest is adequate (`USER-SD-DEC-006`). A keyed digest remains a later option and would add a key-identifier column. |
| Wire encoding | **[Proposed]** Tokens, nonces, binders and CSRF tokens are random bytes encoded URL-safe base64 on the wire (api-contracts §11.1). The digest is taken over the **decoded bytes** and stored raw as `bytea`. |
| Text | **[Proposed]** `text` with `CHECK` length bounds where a bound is known; no `varchar` limits invented. |
| Deletion | **[Decided]** Customers are never deleted in the first release (`USER-DEC-011`). Foreign keys use `ON DELETE RESTRICT` (no cascade). |
| Raw secrets | **[Decided]** No raw token, nonce, binder or CSRF token column exists anywhere. |

## 4. Tables
Column lists are logical-to-physical mappings of data-model §4, §5, §14 and §15.

### 4.1 `customers`
| Column | Type | Null | Notes |
|---|---|---|---|
| `id` | uuid | no | Primary key; database-generated v4. |
| `identity_provider` | text | no | `CHECK` value is `'google'` in the first release. |
| `provider_subject` | text | no | Google `sub`, case-sensitive, immutable. Maximum length **[Evidence]**: verify against Google's documented limit before fixing a `CHECK`. |
| `name` | text | **yes** | `CHECK`: NULL, or non-empty after trimming. Never invented (`USER-DM-DEC-001`). |
| `email` | text | no | Stored exactly as Google supplies it. `CHECK` non-empty. |
| `created_at` | timestamptz | no | Default `now()`. |
| `updated_at` | timestamptz | no | Default `now()`; **[Proposed]** set by the application whenever name or email changes (no trigger). |

Constraints and indexes:
| Name (descriptive) | Definition | Source |
|---|---|---|
| Primary key | `id` | `USER-FR-040` |
| Unique identity | unique (`identity_provider`, `provider_subject`) | `USER-FR-009`, `010`; `USER-DM-AC-033` |
| Unique email, case-insensitive | **[Proposed]** a unique **expression index on the lower-cased email**, so no extension is required. The index exists **only** to enforce integrity and detect collision, never to find or merge a customer (`USER-FR-088`, `USER-FR-005`). | `USER-DM-AC-034`; `USER-AC-042` |

**Email comparison caveat [Open]:** lower-casing is locale- and collation-dependent for non-ASCII addresses. The design assumes the database default produces stable results for the addresses Google returns; this is confirmed with a test insert set when the database exists. No dot or plus-tag normalization is applied (data-model §15.4). A case-insensitive text type (a PostgreSQL extension) is the alternative; it needs its own approval because it adds a dependency on an extension.

### 4.2 `auth_sessions`
| Column | Type | Null | Notes |
|---|---|---|---|
| `id` | uuid | no | Primary key. Used in events; not a credential. |
| `customer_id` | uuid | no | Foreign key to `customers(id)`, `ON DELETE RESTRICT`. |
| `created_at` | timestamptz | no | Default `now()`. |
| `absolute_expires_at` | timestamptz | no | **[Decided]** set at creation to creation + the configured absolute lifetime (90 days approved); never updated (`USER-FR-086`, data-model §15.7). |
| `revoked_at` | timestamptz | yes | Once set, never cleared (data-model §6.3). |
| `revocation_reason` | text | yes | `CHECK` against an enumeration. **[Proposed]** initial values: logout, reuse detected. **[Open]** the final set (data-model §5.1). |
| `csrf_token_digest` | bytea | no | Digest of the session CSRF token (`USER-SD-DEC-028`). |

Indexes: primary key; **[Proposed]** a non-unique index on `customer_id` (customer's sessions; foreign-key checks). **[Open]** an index supporting expiry cleanup is deferred until cleanup is approved (§8).

Immutability: `absolute_expires_at`, `customer_id`, `created_at` and `csrf_token_digest` are not updatable by the application role (column privileges, §6).

### 4.3 `refresh_tokens`
| Column | Type | Null | Notes |
|---|---|---|---|
| `id` | uuid | no | Primary key; safe to appear in events. |
| `session_id` | uuid | no | Foreign key to `auth_sessions(id)`, `ON DELETE RESTRICT`. |
| `token_digest` | bytea | no | Unique. The raw token is never stored. |
| `issued_at` | timestamptz | no | Default `now()`. |
| `expires_at` | timestamptz | no | Stored at issue: the earlier of (now + refresh lifetime, default 7 days) and the session's `absolute_expires_at` (data-model §13.5). |
| `consumed_at` | timestamptz | yes | Set exactly once at rotation; never cleared. |
| `successor_id` | uuid | yes | Foreign key to `refresh_tokens(id)`; **unique**, so a chain cannot fork (`USER-DM-AC-025`). Set in the same transaction that creates the successor. |

Constraints and indexes: primary key; unique `token_digest` (lookup index at refresh and logout); unique `successor_id`; non-unique index on `session_id`.

**Cross-table rule [Proposed]:** "token expiry never later than the session's absolute expiry" cannot be a single-table `CHECK`. It is enforced by the issuing transaction (expiry computed with `LEAST`) and verified by the acceptance check for `USER-AC-030`. A trigger is **not** proposed.

### 4.4 `sign_in_nonces`
| Column | Type | Null | Notes |
|---|---|---|---|
| `nonce_digest` | bytea | no | Primary key (the nonce is found by its digest). |
| `binder_hash` | bytea | no | Hash of the page-held binder, as supplied when the nonce was requested. |
| `created_at` | timestamptz | no | Default `now()`. |
| `expires_at` | timestamptz | no | Creation + the configured nonce lifetime (five minutes approved). |
| `consumed_at` | timestamptz | yes | Set once, atomically (`USER-SEC-014`). |

No relationship to a customer or session. No client address is stored: the per-client cap on outstanding nonces (security-design §4.4) is an **in-process** rate-limit concern (§11.1) and is not represented here **[Open: if a database-backed limiter is ever chosen, this table would need a client key and its own approval]**.

### 4.5 `security_events`
| Column | Type | Null | Notes |
|---|---|---|---|
| `id` | uuid | no | Primary key. |
| `event_type` | text | no | `CHECK` against the **durable** types in security-design §13.4 (sign-in succeeded, refresh rotated, refresh reuse detected, session revoked, logout, nonce replay, nonce invalid, identity conflict, identity unresolved). Failed sign-in, rate-limit rejection and persistence-failed events are **not** durable and have no value here. |
| `occurred_at` | timestamptz | no | Default `now()`. |
| `customer_id` | uuid | yes | **Plain nullable identifier, no foreign key** (Step 5f; `USER-DM-DEC-012`). |
| `session_id` | uuid | yes | Same. |
| `token_record_id` | uuid | yes | Same. |
| `request_id` | text | yes | Server-generated request identifier (api-contracts §13). |
| `reason_code` | text | yes | Enumerated reason code. **[Open]** the set, including the distinct code for the existing-subject email collision (name fixed when the enumeration is approved). |

**Forbidden content [Decided]:** no raw or hashed token, nonce, binder, CSRF token, credential, secret, **email address**, or client IP (`USER-FR-028`, `USER-SEC-008`, `USER-SEC-018`, `USER-AC-042`). There is **no free-text column**, so request-derived text cannot be stored.

Indexes: primary key; **[Proposed]** index on `occurred_at` (review and retention). **[Proposed]** no other index until a query need is approved.

Append-only: the application role has no `UPDATE` privilege on this table (§6).

## 5. Transactions and concurrency
All sequences below run in **one explicit transaction on one connection**. Isolation: **[Proposed]** the default (read committed) is sufficient because every race is resolved by a **conditional update** or a **unique constraint**, not by read-then-write logic.

**Exceptions to fail-closed [Decided, requirements §12.10]:** two steps use a **savepoint** around the event insert so that an event failure rolls back only the event, not the protective or successful state change. The failure is then reported through the independent signal (security-design §13.2). Every other event insert has no savepoint, so its failure aborts the whole transaction (fail closed, `USER-SEC-017`).

| Operation | Steps (one transaction) | Atomicity |
|---|---|---|
| **Issue nonce** | Delete expired nonce rows opportunistically (§8); insert the digest, binder hash and expiry. | One statement group. No event. |
| **Sign in, existing subject** | (1) Consume nonce (conditional update: digest matches, `consumed_at` is null, `expires_at` is in the future; rows changed = 1 or reject). (2) Check the binder hash. (3) Select the customer by (provider, subject). (4) Update name and `updated_at`; update email only if it differs (see the collision path). (5) Insert the session. (6) Insert the sign-in event. | Steps 5 and 6 commit together (fail closed). |
| **Sign in, new subject** | Steps 1 and 2 as above; insert the customer; insert the session; insert the event. | All commit together. |
| **Email collision, existing subject (Exception 2)** | The email update runs inside a **savepoint**. A unique violation on the email index rolls back to the savepoint, leaves the stored email unchanged, and the sign-in continues. The conflict event insert is inside its own savepoint: if it fails, roll back to it and **still commit** the sign-in. | Sign-in is never refused because of the collision or the event. |
| **Email collision, unknown subject** | The customer insert raises a unique violation on the **email** index (distinguished from a violation on the identity index by the constraint that fired). Roll back the transaction (or to a savepoint taken before the insert), consume nothing further, write the conflict event in a fresh statement group, return `409`. | No customer, session or token exists afterwards. |
| **Concurrent first sign-ins** | The same subject: the identity unique index lets one insert win; the loser re-selects the winner's row and proceeds as an existing subject. Different subjects with the same email: one succeeds and one gets `409`. | Resolved by the unique indexes. |
| **Refresh** (after the CSRF checks, read-only, per security-design §10.5) | (1) **One conditional update** marks the presented token consumed, only if its digest matches, it is unconsumed and unexpired, and its session is unrevoked and before its absolute expiry; rows changed = 1 wins. (2) Insert the successor with `LEAST(now + lifetime, session absolute expiry)`. (3) Set `successor_id` on the old token. (4) Insert the rotation event. | All four commit together or not at all (`USER-DM-AC-024`, `USER-DM-AC-038`). |
| **Refresh, token already consumed (reuse)** | The conditional update changes no row; a read finds the digest consumed. Revoke the session (conditional update `revoked_at is null`). Insert the reuse event and the revoke event **inside a savepoint** (Exception 1). Return the generic refresh error. | The revocation always commits. |
| **Refresh, unknown, expired or revoked** | The conditional update changes no row and no consumed record matches: reject generically. Event only when the presented digest is recognized as invalidated (`USER-FR-082`). | No state change. |
| **Logout** | Find the session through the token digest; if found and unrevoked, set `revoked_at` and the reason; insert the logout event. Not found or already revoked: no change, `204`. | Revocation and event commit together; a failed revocation returns `503` (api-contracts §6.3). |
| **Get current customer** | Select by primary key. | Read-only. |

**Ambiguous outcomes [Decided, security-design §8.1]:** if the connection is lost around the commit, the application treats the outcome as unknown, never as a confirmed rollback. Nothing in this schema changes that; **[Evidence #3]** verifies the behavior through each connection route.

## 6. Privileges and row-level security
**[Decided]** least privilege, owner and application separate, RLS as defense in depth and not a substitute (`USER-SEC-016`, `USER-SD-AC-037`). **[Proposed]** grants below; **[Evidence #4–8]** verifies them.

| Principle | Design |
|---|---|
| Ownership | `<owner_role>` owns the schema and tables and runs migrations. `<app_role>` owns nothing. |
| Application role attributes | No superuser, no role creation, no database creation, no row-security bypass, no schema `CREATE`. Not a member of any API-facing role. |
| Schema | `<app_role>` has `USAGE` on `<schema>` only. |
| `customers` | `SELECT`, `INSERT`; `UPDATE` only on `name`, `email`, `updated_at`. |
| `auth_sessions` | `SELECT`, `INSERT`; `UPDATE` only on `revoked_at`, `revocation_reason`. |
| `refresh_tokens` | `SELECT`, `INSERT`; `UPDATE` only on `consumed_at`, `successor_id`. |
| `sign_in_nonces` | `SELECT`, `INSERT`, `UPDATE` on `consumed_at`, and `DELETE` (cleanup of expired rows). |
| `security_events` | `INSERT` and `SELECT` only. No `UPDATE`, no `DELETE` by the application. **[Open]** who deletes events past retention (an owner-run maintenance path is the default proposal; no scheduler is decided). |
| Everything else | No `TRUNCATE`, no `REFERENCES`, no `TRIGGER`, no default privileges for other roles. |
| HTTP-API roles | All privileges on `<schema>` and its tables are revoked from every role the host's HTTP APIs use; the schema is not in the exposed-schemas setting. **[Evidence #6, #8]** |
| RLS | Enabled on every table. The application role is given an explicit policy permitting the operations it holds grants for, so it is not reliant on owner bypass; API roles have no policy and so see nothing. RLS is **not** relied on as the only barrier. **[Evidence #7]** |
| Realtime, functions, views | None of these tables is in a Realtime publication and no exposed function or view reads them. **[Evidence #8]** |

## 7. Migration and ownership model
- **[Decided]** `node-pg-migrate` is an approved development dependency (not installed). **[Proposed]** migrations are ordered files run **only by `<owner_role>`** from a trusted machine, never by the Render runtime, so the owner credential stays off the runtime (`security-design` §14.1, check 9).
- **No migration file exists.** Creating them is implementation and is not authorized.
- The runtime holds only the `<app_role>` credential, supplied through the platform's secret mechanism (`USER-SD-DEC-018`); it is not recorded in any specification.

## 8. Cleanup and retention (provisional)
All periods and cleanup timing are **provisional** (Step 5f). 180 days for durable security events is a **proposed operational default pending privacy and legal review**; it is not a legal requirement.
| Data | Rule | Status |
|---|---|---|
| Expired nonces | Deleted opportunistically at nonce issuance (no scheduler). A **consumed** nonce is kept until its own expiry so replay can be told apart from an unknown nonce; after expiry both are removed. No extra grace period is added. | **[Proposed]** |
| Consumed refresh tokens | **Never** removed before the token's own expiry (reuse recognition, `USER-FR-082`). | **[Decided]** |
| Sessions | Kept while any of their tokens could still be presented and while a reuse investigation may need them. | **[Decided]** minimum |
| Any removal beyond those minimums (expired sessions and tokens, orphaned Profile X sessions) | **No period and no timing is chosen.** | **[Open]** |
| Security events | 180 days proposed; independent of customer, session and token lifecycles; no foreign keys to cascade. Removal mechanism and timing not chosen. | **[Proposed, provisional]** |
| Customers | Not deleted in the first release. | **[Decided]** |
